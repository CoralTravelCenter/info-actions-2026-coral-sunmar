## Фактическое состояние

Старые документы фиксируют исторические проблемы, но значительная часть уже устранена. В текущем коде есть TypeScript, Vitest, composables, нормализация и санитизация внешнего конфига, безопасное определение бренда, дедупликация показов и публичное событие клика. `ant-design-vue` уже удалён. Поэтому повторять старые P0/P1-задачи не нужно.

Актуальные точки улучшения:

1. `src/scripts/info-actions.js` требует вручную комментировать DEV-импорт перед production-сборкой. Это операционный риск попадания тестового конфига в production.
2. Все карточки используют `loading="lazy"`; изображения первого экрана могут ухудшать LCP.
3. В `Card.scss` остаются пять `!important`, а часть цветов SVG и стилей захардкожена.
4. Внешний контракт продолжает принимать legacy `ligal` и строковый `filter`; локальная фикстура активно использует legacy-формат и пустые `entry_point`.
5. Graphify показывает 96 слабо связанных узлов. Для небольшого Vue-островка это отчасти следствие AST-модели и типов, а не основание для архитектурного рефакторинга.
6. Документация местами противоречит текущему коду: например, описывает старые `.js`-модули, прежний способ загрузки данных и уже закрытые задачи.

## План рефакторинга по спринтам

### Спринт 0 — зафиксировать baseline

Цель: обеспечить измеримый и обратимый старт.

- Зафиксировать текущие показатели production-бандла, LCP/CLS и поведение на Coral/Sunmar стендах.
- Проверить реальные цели `coral-bonus-show` и `sunmar-bonus-show` в соответствующих счётчиках.
- Сохранить smoke-checklist: загрузка конфига, фильтры, пагинация, ERID, popup/link, показ бонусного баннера.

Критерий готовности: есть исходные метрики и воспроизводимый checklist. Код не меняется.

### Спринт 1 — безопасный production-конфиг (P0)

Зачем: ручное комментирование импорта — наиболее вероятная причина человеческой ошибки при релизе.

- Заменить безусловный импорт `promotion-settings.js` на автоматический DEV-only механизм, который гарантированно исключается из production-бандла.
- Сделать `check:production-config` обязательной частью общего `check` или CI-пайплайна.
- Добавить тест/проверку, что маркер локального конфига отсутствует в production HTML.
- Обновить README только после утверждения нового процесса.

Затронутые файлы: `src/scripts/info-actions.js`, возможно `src/data/promotions.ts`, `package.json`, `tools/check-production-config.mjs`, тесты и README.

Риск: порядок инициализации `window._promotion_settings`. Нужны отдельные проверки dev и production build.

Критерий готовности: production-сборка не зависит от ручного редактирования исходника и не содержит локальные акции.

### Спринт 2 — контракт внешних данных (P1)

Зачем: центральные Graphify-узлы находятся на границе внешнего конфига; ошибка здесь распространяется на UI, фильтры и аналитику.

- Согласовать с владельцем внешнего скрипта канонические поля: `id`, `filters: string[]`, `legal`, аналитические признаки.
- Оставить legacy-адаптер на ограниченный переходный период с диагностикой использования устаревших полей.
- Усилить проверки дат, URL, дубликатов ID и несовместимых значений без изменения поведения необязательных полей.
- Добавить контрактные фикстуры: каноническая, legacy, частично повреждённая.
- После миграции данных удалить legacy `ligal`/`filter` отдельным изменением, не одновременно с первым этапом.

Затронутые файлы: `src/types/promotion.ts`, `src/data/promoSchema.ts`, `src/utils/configWarnings.ts`, локальная фикстура и соответствующие тесты.

Риск: внешний источник не находится в этом репозитории. Удаление legacy-поддержки нельзя делать до подтверждения владельца данных.

Критерий готовности: валидный канонический конфиг проходит без предупреждений; legacy-конфиг работает, но диагностируется; некорректные записи изолируются предсказуемо.

### Спринт 3 — производительность карточек (P1)

Зачем: оптимизировать пользовательский эффект без изменения бизнес-логики.

- Передавать позицию карточки и назначать первым видимым изображениям `loading="eager"` и `fetchpriority="high"`, остальным оставлять lazy.
- Проверить возможность CDN `srcset`/WebP только после подтверждения поддерживаемых URL-параметров.
- Сравнить LCP/CLS и размер HTML/бандла с baseline.
- Не вводить абстракцию image-компонента, пока оптимизация используется только здесь.

Затронутые файлы: `InfoActions.vue`, `Card.vue`, тесты компонента/логики приоритета.

Риск: слишком много high-priority изображений ухудшит загрузку; лимитировать первым рядом/видимой страницей.

Критерий готовности: LCP не хуже baseline, первый экран загружается приоритетно, остальные изображения остаются ленивыми.

### Спринт 4 — стили и визуальная устойчивость (P2)

Зачем: убрать хрупкую борьбу с глобальными стилями лендинга и централизовать брендовые значения.

- Для каждого из пяти `!important` определить источник конфликта и повысить локальную специфичность минимально необходимым способом.
- Перенести повторяющиеся цвета в существующие CSS custom properties; сохранить различия Coral/Sunmar.
- Проверить responsive-состояния на основных брейкпоинтах и фокус/hover ERID-popover.
- Не выполнять массовое форматирование SCSS.

Затронутые файлы: `Card.scss`, `_variables.scss`, при необходимости локальные стили InfoActions/Tabs.

Риск: глобальные стили CMS могут отличаться от dev. Обязательна проверка на стенде.

Критерий готовности: `!important` отсутствует либо для каждого оставшегося случая документирована неизбежная внешняя причина; визуальных регрессий нет.

### Спринт 5 — документация и контроль архитектуры (P2)

Зачем: текущие документы смешивают историю и актуальное состояние, из-за чего следующий рефакторинг может повторить уже сделанную работу.

- Привести README и REFACTORING к текущим именам `.ts`, способу загрузки и фактическим остаточным задачам.
- Сохранить ANALYSIS-2026 как исторический документ, явно отделив закрытые пункты.
- После завершения production-изменений отдельно обновить Graphify с явного разрешения пользователя и сравнить узлы/циклы.

Критерий готовности: документация описывает текущий код; тесты/check проходят; Graphify не показывает новых циклов или неожиданных архитектурных хабов.

## Рекомендуемый порядок

Начать со Спринта 1: он устраняет релизный риск при минимальном blast radius. Затем выполнить контракт данных, поскольку он влияет на все последующие слои. Производительность и стили держать отдельными спринтами, чтобы метрики и визуальные регрессии можно было оценить независимо.

Перед каждым спринтом требуется отдельное согласование решения и разрешение на изменение production-файлов.
