## 1. Анализ проекта

### 1.1 Что это

Лендинг «Акции» для двух брендов (coral.ru / sunmar.ru) на сборщике `b2c-landing-vite`
(schemaVersion 2). Три блока в `src/order.json`: `text`, `info-actions`, `contacts`.
Реальная логика — только в `info-actions`: Vue-островок, монтируемый в `#info-actions`.

```
scripts/info-actions.js       точка входа блока: createApp + antd(Tooltip, Button) + 3 директивы
components/InfoActions/       InfoActions.vue (табы + список) → Tabs.vue, Card.vue
data/promotions.js            25 записей конфига акций (export PROMOTIONS)
utils/filterFreshOffers.js    фильтр актуальности по датам (dayjs)
directives/                   ymbonus (показ), entry (клик), clipboard (копирование erid)
styles/common/                переменные, миксины, layout, компоненты
```

Поток данных: `PROMOTIONS` → `filterFreshOffers` → нормализация фильтров → `computed`
фильтрация по табу → рендер карточек. Архитектура здравая, объём кода небольшой,
проблемы — точечные.

### 1.2 Что уже хорошо (сделано при миграции)

- конфиг стал ES-модулем, глобал `window._promotion_settings` оставлен как fallback;
- удалены `copy-to-clipboard` / `vue-clipboard`;
- `.no-scrollbar` вынесен в общие утилиты;
- есть JSDoc-тип `PromoConfig`.

### 2.1 Отдельный трек: производительность Vue и семантика (вместо SSR)

SSR/пререндер недоступен, поэтому вытягиваем то, что можно:

**Производительность рантайма**
- убрать `:key="currentFilter"` (C1) — сейчас каждое переключение таба заново создаёт
  все карточки и перезагружает изображения;
- `shallowRef` для списка акций (сделано) — глубокая реактивность на 28 объектах не нужна;
- нормализацию фильтров делать один раз после загрузки, а не в цепочке `computed` (C5, D6);
- один SVG вместо двух на карточку (C10) — минус N лишних DOM-узлов;
- выкинуть `ant-design-vue` (P3-17) — главный вклад в вес бандла.

**Производительность загрузки**
- `width`/`height` на `<img>` (C13) — убирает CLS, критично без SSR;
- первым 2–4 карточкам `loading="eager"` + `fetchpriority="high"`, остальным `lazy` (сейчас
  `lazy` у всех, включая первый экран → LCP страдает);
- `srcset`/`?w=` от CDN + `.webp` там, где ещё `.png`/`.jpg`.

**Семантическая вёрстка**
- секция: `<section>` с заголовком `<h2>`, список акций — `<ul>/<li>` (уже так);
- карточка: `<article>` с осмысленным заголовком (сейчас `<h5>` без иерархии — уровень
  должен следовать за заголовком секции, а не выбираться по размеру шрифта);
- табы: `<nav role="tablist">` + `<button role="tab" aria-selected>` вместо `<li @click>` (C14);
- `<time datetime="2026-09-20">` для срока акции вместо `<span>` — заодно готовит почву
  под микроразметку;
- у ссылки «Подробнее» — `aria-label` с названием акции (сейчас 28 одинаковых «Подробнее»
  подряд для скринридера).

**Микроразметка (позже, отдельной задачей)**
Карточка акции ложится на schema.org. Заготовка на будущее: `ItemList` на `<ul>` и
`Offer`/`SaleEvent` на каждой карточке с `name`, `description`, `image`, `url`,
`validFrom`/`validThrough` (как раз `promo_start`/`promo_end` в ISO). Семантические
`<article>`/`<time>` из пункта выше сделают переход на разметку почти механическим.

## 3. Проблема с Яндекс.Метрикой на продакшене

Найдено **пять** независимых дефектов. Первые три объясняют «цели не приходят»,
четвёртый и пятый — «целей приходит слишком много / данные врут».

### 3.0 Контекст: данные тоже приходят асинхронно

После перевода конфига на внешний скрипт (`window._promotion_settings`) карточки
рендерятся **позже** монтирования приложения. Это усугубляет гонку из 3.1: к моменту
появления карточек во вьюпорте счётчик может быть ещё не готов — и наоборот.
Поэтому отправка целей обязана быть независимой от порядка загрузки (очередь, см. ниже).

### 3.1 ⛔ Гонка с загрузкой счётчика — цели теряются молча (главная причина)

`ymbonus.directive.js`:

```js
seen.add(el);                                   // ← пометили как отправленное
if (typeof window.ym === 'function') {           // ← если счётчика ещё нет — тихо ничего
  window.ym(counterId, 'reachGoal', goal, yaParams);
}
stop();                                          // ← наблюдение остановлено навсегда
```

Порядок операций фатальный: элемент помечается в `seen` и observer останавливается
**до** проверки доступности `window.ym`. Карточки CoralBonus находятся в первом экране и
пересекают вьюпорт сразу после монтирования — то есть в момент, когда счётчик,
подключённый асинхронно (или через GTM/CMP-согласие), ещё не инициализирован.
Результат: цель `coral-bonus-show` не отправляется **никогда**, ретрая нет, ошибки в
консоли нет. На локали/дев-стенде счётчик грузится быстрее (или из кэша) — баг
не воспроизводится, поэтому он и «только на продакшене».

**Фикс:** отправлять через очередь, не завязываясь на готовность `ym`:

```js
// src/config/metrika.js
export function reachGoal(goal, params) {
  // Штатный стаб сниппета Метрики буферизует вызовы до загрузки tag.js.
  // Если сниппета нет вовсе — создаём совместимый буфер сами.
  window.ym = window.ym || function (...args) { (window.ym.a = window.ym.a || []).push(args); };
  window.ym(METRIKA.counterId, 'reachGoal', goal, params);
}
```
и помечать `seen` **только после** фактической отправки. Дополнительно — не вызывать
`stop()` до успешной отправки, а на дев-сборке логировать каждый `reachGoal`.

### 3.2 ⛔ Клик не трекается у 18 из 25 акций

`entry.directive.js`:

```js
const stockName = binding.value != null ? String(binding.value).trim() : null;
if (!stockName) return;   // пусто → директива вообще не инициализируется
```

`entry_point` заполнен лишь у 7 записей конфига; у остальных `undefined` → цель
`entry-point` по клику «Подробнее» не отправляется вообще. Это выглядит как «Метрика
недосчитывает переходы».

**Фикс:** заполнить `entry_point` во всех записях + фолбэк на `id`/`name` акции вместо
раннего `return`.

### 3.3 ⛔ Цель по клику не успевает уйти при переходе

Клик по `<a href="..." target="_blank">` — ок, но кнопка-фолбэк (`v-else`) и любой
переход в том же табе приводят к выгрузке страницы сразу после `reachGoal`; XHR
Метрики отменяется.

**Фикс:** использовать `callback` Метрики с таймаутом, либо `sendBeacon`-режим счётчика:

```js
window.ym(counterId, 'reachGoal', goal, params, () => { /* navigate */ });
```
(и включить `params: { defer: true }`/`sendBeacon` в настройках счётчика).

### 3.4 ⚠️ Дублирование целей при переключении табов (данные завышены)

```text
// InfoActions.vue
<ul class="cards-container" :key="currentFilter">   // ← весь список пересоздаётся

// ymbonus.directive.js
unmounted(el) { seen.delete(el); }                  // ← дедупликация обнуляется
```

`seen` — `WeakSet` **по DOM-элементу**. При каждом переключении фильтра `:key` уничтожает
`<ul>` целиком, директивы размонтируются, `seen.delete(el)` стирает память, новые
элементы снова попадают во вьюпорт → `coral-bonus-show` отправляется повторно.
Пользователь, пощёлкавший табы, генерирует десятки показов одной и той же акции.

**Фикс:** убрать `:key="currentFilter"` с `<ul>` (нужно и по перформансу — см. C1) и
ключевать дедупликацию по **идентификатору акции**, а не по элементу:
`const seen = new Set() // ids`, без `seen.delete` в `unmounted`.

### 3.5 ⚠️ Неверный бренд/счётчик и стухшие параметры

- Бренд определяется тремя разными способами (`origin.includes('coral.ru')` vs
  `host.includes('coral')`). На любом домене, где нет подстроки `coral` (превью-стенд,
  партнёрский поддомен, мобильное webview), цели уходят в **счётчик Sunmar 215233** —
  то есть в чужой счётчик. Плюс `isBonus` (`/bonus/i`) срабатывает на фильтре `CoralBonus`
  даже на sunmar-сборке, и там шлётся `sunmar-bonus-show` с coral-акциями.
- Обе директивы имеют только хук `mounted`, без `updated`. В связке с неуникальным
  `:key="promotion.name"` (C2) Vue переиспользует DOM-узел под другую акцию, а
  `bannerName` / `stockName` остаются от предыдущей → в Метрику уходит **чужое название баннера**.

**Фикс:** `brand.js` (P1-6) как единственный источник счётчика; добавить хук `updated`
в обе директивы; уникальный `id` в `:key`.

### 3.6 Порядок работ по Метрике

| Шаг | Что | Эффект |
|---|---|---|
| 1 | Очередь `reachGoal` + `seen` после отправки (3.1) | возвращает потерянные показы |
| 2 | Убрать `:key="currentFilter"`, дедуп по `id` акции (3.4) | убирает завышение показов |
| 3 | `entry_point` во всех записях + фолбэк (3.2) | возвращает клики |
| 4 | `brand.js` + хук `updated` в директивах (3.5) | правильный счётчик и корректные названия |
| 5 | `callback`/`sendBeacon` на клике (3.3) | добивает потери на переходах |
| 6 | dev-логирование всех `reachGoal` | верификация на стенде |

Отдельно: проверить в интерфейсе Метрики, что цели `coral-bonus-show`, `sunmar-bonus-show`,
`entry-point` **созданы** в соответствующих счётчиках (96674199 / 215233) — `reachGoal`
на несуществующую цель отрабатывает молча.
