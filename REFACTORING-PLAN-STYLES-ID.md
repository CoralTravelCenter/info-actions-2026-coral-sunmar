# План рефакторинга стилей и поддержки стабильного ID акции

Дата подготовки: 2026-09-10.

## 1. Цели

1. Убрать зависимость Vue-компонентов от глобальных правил и внешних DOM-селекторов.
2. Сделать стили каждого компонента явными для двух брендов: Coral и Sunmar.
3. Провести стабильное поле `id` из внешнего конфига через внутреннюю модель и компонентный слой в событие `promotion-card:click`.
4. Сохранить текущее пользовательское поведение, адаптивность и публичное имя DOM-события.

## 2. Подтверждённое текущее состояние

Навигация выполнена по `graphify-out/graph.json`, затем найденные точки сверены с
исходным кодом. Граф показывает следующие основные цепочки:

```text
window._promotion_settings
  → getPromotions()
  → normalizePromotions()
  → Promotion
  → InfoActions.vue
  → Card.vue

Card click
  → InfoActions.vue
  → usePromotionContext.publishPromotionClick()
  → dispatchPromotionClick()
  → document: "promotion-card:click"
  → внешний Coral/Sunmar-скрипт Метрики
```

### 2.1. Стили

- `InfoActions.vue` подключает `src/styles/info-actions.scss` как scoped-стили.
- `Card.vue` и `Tabs.vue` имеют собственные SCSS-файлы, но Sunmar-варианты ищут
  внешний предок `[data-brand='sunmar']`.
- Бренд устанавливается императивно на mount-элементе `#info-actions` в
  `src/scripts/info-actions.js`.
- `src/styles/common/_layout.scss` глобально влияет на `h1–h5`, `p`, `img`,
  `box-sizing` и заголовок блока.
- `src/styles/common/_components.scss` глобально определяет `.prime-btn` и
  `.no-scrollbar`; эти классы используются внутри Vue-компонентов.
- `src/styles/info-actions.scss` содержит `:global(...)` для Sunmar-кнопок.

Из-за этого внешний CSS-контекст является частью неявного API компонентов: компонент
может выглядеть иначе или сломаться при переносе, изменении wrapper-разметки либо
порядка подключения общих стилей.

### 2.2. Стабильный `id`

- Обновлённые локальные конфиги Coral и Sunmar уже содержат стабильный строковый `id`.
- Внешние скрипты Метрики уже выбирают цель по `event.detail.id`.
- `PromotionConfig` и нормализованная модель `Promotion` пока не содержат `id`.
- `normalizePromotion()` не переносит `id` из конфига.
- `PromotionClickDetail` содержит только `name` и `url`.
- `publishPromotionClick()` не передаёт `id`.
- Vue-список использует изменяемое название `promotion.nameText` как `key`.

Следовательно, текущий компонентный слой обрывает уже подготовленный контракт между
конфигом и внешней Метрикой.

## 3. Архитектурные решения

### 3.1. Владение стилями

Каждый Vue-компонент должен владеть:

- базовой геометрией и состояниями своих элементов;
- Coral-вариантом;
- Sunmar-вариантом;
- локальными reset-правилами, без которых компонент зависит от CMS или общего CSS.

Бренд следует передавать компонентам явно через типизированный prop и отражать на
корневом DOM-узле компонента через модификатор класса или локальный `data-brand`.
Предпочтительный контракт:

```text
InfoActions(brand)
  ├─ Tabs(brand)
  └─ Card(brand)
```

Это устраняет скрытую зависимость от `[data-brand]` выше границы компонента и делает
оба брендовых варианта проверяемыми изолированно.

Общие SCSS-ресурсы допустимы только как compile-time инструменты: токены, функции и
миксины без генерации глобальных селекторов. Не следует создавать один новый
глобальный файл с теми же правилами под другим именем.

### 3.2. Контракт `id`

`id` должен быть обязательным полем внешнего и внутреннего контрактов:

```text
PromotionConfig.id
  → normalizePromotion().id
  → Promotion.id
  → :key="promotion.id"
  → publishPromotionClick({ id, nameText, url })
  → PromotionClickDetail.id
  → event.detail.id
```

Почему обязательным: внешний потребитель использует поле как стабильную идентичность,
поэтому молчаливый fallback на `name` вернёт исходную проблему при переименовании
акции. Некорректные или повторяющиеся ID должны обнаруживаться до рендера.

`name` и `url` можно оставить в событии для диагностики и обратной совместимости,
однако маршрутизация целей должна выполняться только по `id`.

## 4. Спринты реализации

### Спринт 0. Зафиксировать визуальную и контрактную базу

Цель: создать safety net до структурных изменений.

Работы:

1. Зафиксировать контрольные состояния Coral/Sunmar для mobile, tablet и desktop:
   сетка, табы, карточка, CTA, «Показать ещё», пустое состояние, предупреждение,
   ERID-popover и fixed navigation.
2. Добавить компонентные проверки, подтверждающие явную передачу бренда и наличие
   брендового модификатора на корневых узлах `InfoActions`, `Tabs` и `Card`.
3. Добавить контрактные тесты текущего DOM-события до изменения его payload.

Критерий готовности: есть воспроизводимая база, позволяющая отличить рефакторинг от
непреднамеренного визуального или поведенческого изменения.

### Спринт 1. Провести `id` через модель данных

Цель: создать единый обязательный идентификатор акции внутри приложения.

Затрагиваемые точки:

- `src/types/promotion.ts`;
- `src/data/promoSchema.ts`;
- `src/data/promoSchema.test.ts`;
- `src/data/promotionDiagnostics.ts` и его тесты.

Работы:

1. Добавить `id: string` в `PromotionConfig` и `Promotion`.
2. Добавить `id` в `REQUIRED_FIELDS` и нормализовать его через существующий
   `normalizeString()`.
3. Перенести дедупликацию с `nameText` на `id`.
4. Считать пустой и повторяющийся `id` ошибкой конфигурации, из-за которой запись не
   попадает в UI.
5. Оставить одинаковые названия допустимыми: отображаемый текст больше не является
   идентичностью сущности.
6. Обновить сообщения диагностики так, чтобы проблемная запись по возможности
   обозначалась через `id` и человекочитаемое имя.

Тест-кейсы:

- `id` нормализуется и присутствует в `Promotion`;
- запись без `id` отклоняется;
- повторяющийся `id` отклоняется;
- одинаковые `name` при разных `id` допустимы;
- пробелы вокруг `id` не создают две разные сущности.

Критерий готовности: любая отрисованная акция имеет непустой уникальный `id`.

### Спринт 2. Передать `id` через компонент в Метрику

Цель: замкнуть уже подготовленный внешний аналитический контракт.

Затрагиваемые точки:

- `src/components/InfoActions/InfoActions.vue`;
- `src/composables/usePromotionContext.ts` и его тесты;
- `src/analytics/promotionEvents.ts` и его тесты.

Работы:

1. Использовать `promotion.id` как Vue `key` карточки.
2. Расширить вход `publishPromotionClick()` полем `id`.
3. Добавить `id` в `PromotionClickDetail` и `CustomEvent.detail`.
4. Сохранить синхронную отправку события и его имя `promotion-card:click`.
5. Не переносить таблицу соответствий ID → цель внутрь Vue: она остаётся во внешних
   брендовых скриптах Метрики.

Тест-кейсы:

- клик публикует точный стабильный `id`;
- вместе с `id` сохраняются ожидаемые `name` и `url`;
- внешний слушатель получает событие синхронно;
- неизвестный ID не приводит к ошибке во внешнем скрипте и не отправляет цель.

Критерий готовности: ID из конфига без преобразований доступен как
`event.detail.id`, и существующие Coral/Sunmar-обработчики могут выбрать нужную цель.

### Спринт 3. Сделать бренд явным контрактом компонентов

Цель: подготовить стили к локализации без изменения внешнего вида.

Затрагиваемые точки:

- `InfoActions.vue`;
- `Tabs.vue`;
- `Card.vue`;
- соответствующие компонентные тесты.

Работы:

1. Ввести единый экспортируемый тип `Brand = "coral" | "sunmar"`, если его ещё нет
   в публичном контракте `src/config/brand.ts`.
2. Передавать `brand` из `InfoActions` в `Tabs` и `Card` через props.
3. Добавить каждому компоненту локальный брендовый модификатор, например
   `component--coral` / `component--sunmar`.
4. Убрать прямой импорт глобального `BRAND` из `Tabs.vue`: дочерний компонент не должен
   самостоятельно читать окружение.
5. Оставить `target.dataset.brand` временно только для внешней разметки, если она ещё
   нужна вне Vue; компонентные стили больше не должны от него зависеть.

Критерий готовности: каждый компонент можно смонтировать в изоляции для любого бренда
без настройки DOM-предка.

### Спринт 4. Локализовать стили `Card`

Цель: убрать влияние глобальных правил на карточку.

Работы:

1. Перенести в `Card.scss` используемые карточкой свойства `.prime-btn`, `h3`, `p` и
   `img`, задавая их через собственные классы карточки.
2. Разделить SCSS на базовую часть и явные Coral/Sunmar-модификаторы.
3. Заменить `[data-brand='sunmar'] .promo-card` локальным селектором корня карточки.
4. Сохранить состояния CTA: default, hover, active, focus-visible и disabled.
5. Проверить размеры изображения, footer-layout, ERID-popover и reduced motion для
   обоих брендов.

Критерий готовности: `Card` визуально корректен без глобальных `section.coral`,
`.prime-btn` и внешнего `[data-brand]`.

### Спринт 5. Локализовать стили `Tabs`

Цель: сделать навигацию независимой от общих utility-классов и внешнего бренда.

Работы:

1. Перенести поведение `.no-scrollbar` в локальный класс списка табов.
2. Заменить `[data-brand='sunmar'] .tabs-navigation` локальным брендовым
   модификатором.
3. Явно описать Coral/Sunmar цвета, фон, радиусы, font-weight и active-состояние.
4. Сохранить mobile horizontal scroll, desktop layout и fixed/hidden состояния.
5. Не менять семантику `<button aria-pressed>` в рамках стилевого рефакторинга.

Критерий готовности: `Tabs` изолированно отображает оба бренда и не использует
глобальные utility-классы.

### Спринт 6. Локализовать стили `InfoActions` и очистить globals

Цель: завершить перенос владения стилями внутрь компонентов.

Работы:

1. Оставить в стилях `InfoActions` только layout контейнера, сетку, empty state,
   предупреждение и кнопку пагинации.
2. Добавить локальные Coral/Sunmar-варианты для сетки, текста и CTA «Показать ещё».
3. Удалить `:global(#info-actions[data-brand='sunmar'] .prime-btn)`.
4. После проверки всех потребителей удалить из common-слоя только те правила
   `.prime-btn`, `.no-scrollbar`, `h3`, `p`, `img`, которые больше не нужны другим
   блокам. Если другие блоки используют их, оставить существующее поведение для них,
   но исключить зависимость `InfoActions` за счёт локальной специфичности.
5. Глобальный `box-sizing` не переносить механически в каждый элемент: определить его
   как host-level baseline либо локально ограничить деревом компонента.
6. Правило заголовка `.info-actions-title`, находящегося вне Vue mount-point, оставить
   во внешнем layout-слое до отдельного согласованного изменения разметки CMS.

Критерий готовности: удаление глобальных компонентных правил не меняет внешний вид
`InfoActions`, `Card` и `Tabs`; во Vue-компонентах отсутствуют `:global` и брендовые
селекторы, зависящие от предка за границей компонента.

### Спринт 7. Интеграционная проверка и выпуск

Работы:

1. Запустить узкие тесты нормализации, аналитического события и затронутых
   компонентов.
2. Выполнить проектные проверки:

   ```bash
   npm run test:run
   npm run typecheck
   npm run check
   ```

3. На стендах обоих брендов проверить click-through для ID, перечисленных во внешних
   скриптах Метрики.
4. Убедиться, что переименование `name` при неизменном `id` не меняет выбранную цель.
5. Проверить отсутствие двойных событий при ссылке и popup-кнопке.
6. Выполнить визуальную регрессию на контрольных ширинах и состояниях из спринта 0.
7. Перед production-сборкой использовать существующий процесс отключения локального
   конфига и `npm run check:production-config`.

Критерий готовности: тесты и проектные проверки проходят, оба бренда визуально
соответствуют базе, Метрика получает стабильный ID.

## 5. Рекомендуемая декомпозиция изменений

Чтобы review оставался локальным и обратимым, не смешивать всё в один patch:

1. Контракт и нормализация `id` + тесты.
2. Event payload и Vue `key` + тесты интеграции.
3. Явная передача бренда без визуальных изменений.
4. Локализация `Card`.
5. Локализация `Tabs`.
6. Локализация `InfoActions` и удаление подтверждённо неиспользуемых globals.
7. Интеграционная и визуальная проверка.

## 6. Риски и меры контроля

| Риск | Последствие | Контроль |
|---|---|---|
| Сделать `id` необязательным | Метрика снова зависит от нестабильных данных | Обязательное поле и отбрасывание невалидной записи |
| Оставить дедупликацию по `name` | Разные акции с одинаковым заголовком конфликтуют | Дедупликация и Vue `key` по `id` |
| Удалить globals до переноса всех правил | Визуальная регрессия компонентов | Перенос по одному компоненту и контрольная база |
| Смешать базовые и брендовые правила | Рост дублирования и неясный cascade | База + два явных локальных модификатора |
| Привязать компонент к `#info-actions` | Невозможность изолированного использования | Props и модификатор на корне компонента |
| Изменить DOM и CSS одновременно | Сложный review и поиск регрессии | Отдельный спринт для брендового контракта |
| Удалить common-правило, используемое другим блоком | Регрессия за пределами задачи | Перед удалением проверить только граф/импорты и фактических потребителей |
| Изменить имя или асинхронность события | Поломка внешней интеграции | Сохранить `promotion-card:click` и синхронный dispatch |

## 7. Definition of Done

- `PromotionConfig.id` и `Promotion.id` обязательны.
- Невалидные и повторяющиеся ID диагностируются и не рендерятся.
- Vue `key` основан на `promotion.id`.
- `promotion-card:click` содержит стабильный `detail.id`.
- Внешние Coral/Sunmar-обработчики получают ID без преобразования.
- `InfoActions`, `Card` и `Tabs` имеют локальные стили Coral и Sunmar.
- Дочерние компоненты не читают бренд из глобального окружения.
- Компонентные стили не зависят от `section.coral`, `#info-actions`, внешнего
  `[data-brand]`, `.prime-btn` или `.no-scrollbar`.
- Визуальное поведение на согласованных ширинах и интерактивных состояниях сохранено.
- Проходят `test:run`, `typecheck` и `check`.

## 8. Вне текущего scope

- Изменение таблиц соответствия ID → цель Метрики: они уже обновлены внешним слоем.
- Редизайн карточек или табов.
- Замена SCSS-стека либо внедрение нового CSS framework.
- Изменение CMS-разметки и внешнего заголовка блока без отдельного согласования.
- Массовая очистка стилей других блоков.
